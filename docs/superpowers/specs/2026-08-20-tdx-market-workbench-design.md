# 通达信全市场现代看板设计规格

- 日期：2026-08-20
- 状态：用户已确认，可进入实施计划
- 开发仓库：`tdx-market-workbench`
- 开发分支：`codex/market-workbench`

## 1. 产品摘要

本项目是在单台 Windows 电脑上运行的通达信全市场行情与资金工作台。系统在交易时段持续采集沪深北全部 A 股，以及通达信全部行业、概念板块的分钟行情和主力净流入数据，使用户切换到任意板块或个股时，都可以立即查看当日从开盘到当前时刻的完整曲线，并可回放历史交易日。

系统面向本地单用户，桌面端优先，强调高信息密度、低操作延迟和数据质量透明。首期聚焦行情、K 线、技术指标和资金数据，不建设新闻、公告、研报或完整基本面资讯系统。

## 2. 目标与非目标

### 2.1 首期目标

1. 核心内容是板块和个股的主力资金净额分时曲线；两类标的都必须支持主力、超大单和大单等可用资金口径。
2. 覆盖沪深北全部 A 股和通达信全部行业、概念板块。
3. 无论用户是否自选或查看，所有标的都持续形成分钟数据。
4. 交易期间每分钟提交一批全市场行情与资金记录。
5. 任意切换板块或个股时，直接读取已经采集的完整日内曲线。
6. 点击板块后展示全部成分股，并按指定分钟的主力净流入排序。
7. 点击任何个股后展示实时行情、盘口、分层资金曲线、K 线及常用技术指标。
8. 支持历史交易日回放，图表、排行和指标共享同一个时间游标。
9. 分钟数据默认保留最近 30 个交易日，并允许在页面中修改。
10. 采集与用户访问隔离；采集阻塞或重连不得阻塞 API 和历史查询。
11. 对延迟、估算、校准和缺口进行明确标记，不伪造数据完整性。

### 2.2 首期非目标

- 不提供下单、自动交易或券商账户连接。
- 不提供新闻、公告、财报、研报等资讯聚合。
- 不建设互联网多租户、权限、计费或云端同步系统。
- 不承诺盘中每个分钟点都与通达信客户端官方资金值逐点完全一致；盘中采用混合口径，收盘后使用官方最终值校准。
- 手机端首期只保证核心内容可查看，不提供完整的移动交易工作台体验。

## 3. 已确认约束

- 部署环境：单台 Windows 电脑，本地单用户。
- 服务运行：开机自启，交易时段常驻。
- 前端：延续 Vue 3、TypeScript、Vite、Naive UI 和 ECharts。
- 后端：延续 Python 和 FastAPI，并拆分采集、查询和维护职责。
- 数据来源：本机通达信目录、`easy-tdx` MAC 协议和 `pytdx` 行情协议。
- 资金口径：主力净额全市场覆盖；板块和个股同时支持主力、超大单、大单等分层口径。盘中混合采集，热门标的优先获取官方值，收盘统一校准。
- 主要屏幕：1920×1080、2K 和普通笔记本宽度。
- 分钟保留：默认最近 30 个交易日，可由页面设置。
- 日 K 保留：长期保留，不受分钟回放保留期限制。

## 4. 总体架构

系统采用本地多进程架构，对用户而言仍是一套一键启动的产品。

```text
通达信本地目录 / TDX MAC / pytdx 行情节点
                  │
                  ▼
        Collector 采集服务
        ├─ 市场目录同步
        ├─ 全市场行情采集
        ├─ 资金采集与聚合
        ├─ 当前标的优先队列
        └─ 分钟批量提交
                  │
          ┌───────┴────────┐
          ▼                ▼
    当日 SQLite 热库    元数据 SQLite
          │                │
          └───────┬────────┘
                  ▼
           FastAPI 查询服务
          ├─ 实时/历史查询
          ├─ 板块与成分股
          ├─ 个股详情/K 线
          ├─ 回放游标数据
          └─ WebSocket 推送
                  │
                  ▼
             Vue 桌面看板

收盘后：Maintenance 维护任务
当日热库 → 校准/校验 → Parquet 分区 → DuckDB 历史查询
```

### 4.1 Collector 采集服务

Collector 是当日热库的唯一写入者，负责所有与通达信网络接口相关的工作。它不处理页面请求。其内部包含独立连接池和任务队列：

- 基线队列保证全市场每分钟覆盖。
- 优先队列提高当前查看、自选和异常补采标的的刷新频率。
- 优先任务不能挤占下一轮全市场分钟任务的时间预算。
- 每一分钟任务都有唯一批次 ID，可安全重试和幂等写入。
- Collector 使用进程级单实例锁，防止两个采集进程同时写入同一个交易日热库。

### 4.2 FastAPI 查询服务

API 服务只读当日热库和历史 Parquet。它可以写入独立的元数据数据库，用于保存设置、自选和采集优先级请求，但不能直接写行情分钟表，也不能直接调用通达信行情接口。

Collector 离线时，API 继续提供最后一次成功提交的数据和全部历史数据，并在响应中返回数据时间、覆盖率、延迟和健康状态。

### 4.3 Maintenance 维护任务

Maintenance 在收盘后或手动触发时运行，负责：

- 收盘官方值校准。
- 数据完整性检查与可恢复缺口补采。
- 当日热库压缩为 Parquet 分区。
- 归档校验和原子发布。
- 根据页面设置执行保留期清理。
- 日 K 数据更新和长期保存。

维护任务失败不影响 API 读取已经发布的历史分区，也不影响下一交易日 Collector 创建新的热库。

### 4.4 前端

前端使用构建后的静态文件，由 API 服务托管。开发环境仍可使用 Vite。首期不引入独立前端服务，以减少本机进程数量。

## 5. 市场目录与采集流程

### 5.1 开盘前同步

每个交易日开盘前同步：

- 沪市、深市、北交所全部 A 股证券目录。
- 股票代码、名称、市场、上市状态和交易状态。
- 通达信行业、概念板块目录。
- 板块与成分股的多对多关系。
- 前一交易日收盘价和必要的日线基准。

目录同步结果写入元数据数据库并带版本号。当天同步失败时，可以使用最近一次成功版本，但页面必须显示目录版本日期。

### 5.2 交易期间行情采集

行情连接池每 5 秒批量请求全市场报价。`pytdx` 单批数量受限，因此采集器按市场和批次拆分，允许多个受控连接并行执行。

分钟结束时，Collector 根据该分钟内的快照生成：

- 分钟开、高、低、收。
- 分钟成交量和成交额增量。
- 累计成交量和成交额。
- 最新价、涨跌额、涨跌幅、振幅等可直接计算字段。

无成交不等于采集缺口：如果该标的在本分钟被成功观测且累计字段没有变化，则生成合法的“无成交”分钟记录；如果没有成功观测，则记录为缺口或过期数据。

### 5.3 交易期间资金采集

盘中资金采用混合口径：

1. 通过行业板块成分接口批量取得成分股累计主力资金，形成全市场基础覆盖。
2. 对未被行业目录覆盖或本轮缺失的股票，进入单股官方资金轮询队列。
3. 当前页面正在查看的股票、自选股和异常标的进入优先队列，使用独立连接获取更高频的官方资金和分时形状。
4. 行业和概念板块的盘中资金由成分股分钟资金聚合生成。
5. 官方板块汇总接口在滚动队列中采集，用作板块累计值校准锚点。

每个资金点同时保存 `source` 和 `quality`，不允许只保存一个无法解释来源的数值。

主力净额是每只股票和每个板块必须具备的核心序列。超大单、大单等分层资金在官方接口提供时直接采用；官方接口只提供主力汇总时，使用通达信分笔成交方向和成交额阈值估算分层曲线，并为每个分层字段单独标记来源与质量。板块分层资金由成分股对应分层聚合，再用可获得的官方板块数据校准。

当主力总额与超大单、大单来自同一分笔估算口径时，主力净额等于超大单与大单净额之和；当主力总额来自官方接口而分层来自估算时，界面分别展示其来源，不宣称三者严格可加和。主力官方总额始终是主曲线和收盘校准锚点。

### 5.4 分钟提交

每个交易分钟结束后执行一次批量事务：

1. 冻结本分钟行情快照。
2. 合并资金采集结果。
3. 计算板块聚合值和上涨/下跌家数。
4. 写入股票、板块和采集状态表。
5. 提交后更新“最新已完成分钟”指针。
6. API 只读取已完成分钟，不读取正在写入的批次。

单分钟全市场采集、计算和提交的硬性预算为 45 秒，为失败重试和下一分钟调度预留空间。

### 5.5 午间、收盘和中途启动

- 午间休市不生成虚假的连续交易分钟；时间轴保留 11:30 到 13:00 的自然间隔。
- 15:00 后冻结盘中写入，进入补采、校准和归档阶段。
- 程序中途启动时，先建立当天预期时间轴，再从通达信可用的分时、K 线和资金接口补齐缺失数据。
- 无法恢复的分钟保留缺口记录，前端显示断点和原因。
- 断线恢复后只补缺失批次，幂等键防止重复记录。

## 6. 资金口径与校准

### 6.1 数据质量枚举

每个分钟资金点使用以下质量状态之一：

- `official`：直接来自通达信官方累计资金接口。
- `aggregated`：由成分股官方或混合资金聚合得到。
- `estimated`：由分笔方向、momentum 或其他可解释形状估算。
- `calibrated`：收盘后使用官方最终值校准。
- `stale`：沿用最近观测值，但本分钟未取得新资金观测。
- `gap`：没有足够数据生成可信数值。

`source` 进一步记录具体来源，例如 `tdx_mac_capital_flow`、`tdx_board_members`、`tdx_tick_momentum`、`pytdx_transactions` 或 `constituent_sum`。

### 6.2 收盘校准规则

- 原始盘中曲线永久保留到对应交易日归档完成，不被原地覆盖。
- 若存在稳定的估算曲线和官方收盘累计值，优先使用比例缩放，使曲线终点与官方值一致。
- 当估算终值接近零、与官方终值方向冲突或比例超出安全范围时，不做失真缩放；改为按各分钟成交额权重分配差额，并将质量标记为 `calibrated`。
- 板块使用同样原则，以官方板块收盘汇总为锚点。
- 校准算法带版本号；历史回放响应返回算法版本和校准时间。

## 7. 存储设计

### 7.1 元数据数据库

`data/meta/market_meta.sqlite` 保存：

- `security_master`
- `sector_master`
- `sector_membership`
- `trading_calendar`
- `user_settings`
- `watchlists`
- `collection_priority`
- `schema_migrations`

API 可以修改设置、自选和优先级请求；目录表由 Collector 或 Maintenance 更新。

### 7.2 当日热库

每个交易日使用独立文件：`data/hot/YYYY-MM-DD.sqlite`。数据库开启 WAL，Collector 使用批量事务写入，API 使用只读连接。

核心表：

#### `stock_minute`

- `trade_date`
- `minute`
- `symbol`
- `open`、`high`、`low`、`close`
- `volume_delta`、`amount_delta`
- `volume_cum`、`amount_cum`
- `change_pct`
- `main_net_delta`、`main_net_cum`
- `super_net_delta`、`super_net_cum`
- `large_net_delta`、`large_net_cum`
- `medium_net_delta`、`medium_net_cum`
- `small_net_delta`、`small_net_cum`
- `source`、`quality`
- `tier_sources`、`tier_qualities`
- `observed_at`、`batch_id`

唯一键为 `(trade_date, minute, symbol)`。

#### `sector_minute`

- `trade_date`
- `minute`
- `sector_id`
- `price`、`change_pct`
- `main_net_delta`、`main_net_cum`
- `super_net_delta`、`super_net_cum`
- `large_net_delta`、`large_net_cum`
- `medium_net_delta`、`medium_net_cum`
- `small_net_delta`、`small_net_cum`
- `official_main_net_cum`
- `up_count`、`down_count`、`member_count`
- `source`、`quality`
- `tier_sources`、`tier_qualities`
- `observed_at`、`batch_id`

唯一键为 `(trade_date, minute, sector_id)`。

#### `collection_status`

- `trade_date`、`minute`、`batch_id`
- `expected_stocks`、`collected_stocks`
- `expected_sectors`、`collected_sectors`
- `duration_ms`
- `coverage_pct`
- `status`
- `error_summary`

#### `data_gap`

- 标的类型、标的 ID、交易日、分钟。
- 缺口原因、首次发现时间、重试次数、最终状态。

### 7.3 历史分区

收盘后发布：

- `data/history/entity=stock/trade_date=YYYY-MM-DD/*.parquet`
- `data/history/entity=sector/trade_date=YYYY-MM-DD/*.parquet`

API 使用 DuckDB 直接查询 Parquet，不维护一个由多个进程同时写入的 DuckDB 数据库文件。归档先写入临时目录，行数、唯一键和时间范围校验通过后再原子重命名到正式分区。

### 7.4 K 线与指标

- 日 K 对全市场每日同步并长期保留。
- 周 K、月 K 由日 K 聚合。
- 1/5/15/30/60 分钟 K 优先由已保存分钟行情聚合；缺失历史通过独立采集任务获取并缓存。
- MA、MACD、KDJ、RSI 和 BOLL 基于统一 K 线数据计算，不单独永久存储所有组合结果。
- 当前页面查询 K 线时，API 只读缓存；缺失数据通过元数据任务队列通知 Collector 获取，API 不直接连接通达信。

### 7.5 保留策略

- 分钟股票、板块和回放数据默认保留最近 30 个交易日。
- 页面允许输入新的交易日数量，并显示预计磁盘占用。
- 新设置从下一次收盘维护任务起生效，也可以手动执行维护。
- 缩短保留期需要用户二次确认；删除动作只针对已成功归档并超过保留期的明确分区。
- 日 K 和目录数据长期保留。

## 8. API 边界

首期 API 采用 `/api/v1` 版本前缀。具体字段以 OpenAPI 契约测试固定。

### 8.1 市场与健康

- `GET /api/v1/health`
- `GET /api/v1/market/status`
- `GET /api/v1/market/coverage?date=&minute=`
- `GET /api/v1/trading-dates`

### 8.2 板块

成员排行在服务端按指定分钟连接 `sector_membership` 和 `stock_minute`，避免前端拉取全市场后自行计算。

### 8.3 个股

- `GET /api/v1/replay/{date}/manifest`

- `GET /api/v1/settings/retention`
- `PUT /api/v1/settings/retention`

### 8.5 实时推送

`WS /api/v1/ws/market` 推送最新已完成分钟、覆盖率、健康状态和当前订阅标的的快速更新。WebSocket 断开时，前端退化为短轮询，不影响基本使用。

所有数据响应包含：

- `trade_date`
- `as_of`
- `latest_complete_minute`
- `source`
- `quality`
- `coverage_pct`
- `is_calibrated`
- `fund_tiers`

## 9. 页面与交互设计

### 9.1 全局顶部栏

顶部栏持续展示：

- 市场状态和当前交易日。
- 最新完成分钟、采集延迟和全市场覆盖率。
- 全局股票/板块搜索。
- 实时模式或回放模式。
- 日期选择、主题和设置入口。

全局搜索支持代码、股票名称和板块名称，并提供键盘快速入口。

### 9.2 板块工作台

采用主从布局：

- 左侧：行业、概念、自选板块列表。
- 主区上部：当前板块行情头部和主力资金分时曲线。
- 主区下部：全部成分股排行。

板块列表支持按主力净流入、涨跌幅和资金变化速度排序。板块资金图以主力净额分时曲线为默认核心视图，支持切换主力、超大单、大单等可用口径，并可叠加板块价格或涨幅。

成分股表默认按指定分钟的主力净流入降序，显示股票、价格、涨跌幅、主力净流入、成交额、换手率、质量和更新时间。点击任何股票进入统一个股工作台。

### 9.3 个股工作台

个股页面包含：

- 行情头部：价格、涨跌幅、开高低收、成交量额、换手率、振幅和量比。
- 图表标签：资金分时、价格分时、K 线。
- 个股资金分时以主力净额曲线为默认核心视图，与板块一致支持主力、超大单、大单等可用口径，并展示每条曲线的来源和质量。
- K 线周期：日、周、月、1/5/15/30/60 分钟。
- 指标：MA、MACD、KDJ、RSI、BOLL，可按需开启。
- 侧区：五档盘口、资金构成、所属板块。
- 所属板块可点击返回对应板块工作台。

板块成分股和自选股共用同一个详情页面与数据接口。

### 9.4 历史回放

选择历史交易日后进入回放模式：

- 初始游标位于 09:30。
- 支持播放、暂停、拖动和 1×、5×、15×、30×速度。
- 资金曲线、价格图、板块排行、成分股排行和指标共享一个分钟游标。
- 用户跳转分钟时，优先返回当前可视范围数据，避免重复加载整日全市场数据。
- 返回实时模式后自动跳转到最新已完成分钟。

### 9.5 响应式策略

- 1920×1080 和 2K 使用完整主从布局。
- 普通笔记本宽度可以折叠左侧列表和盘口侧区。
- 手机端改为单列标签式浏览，只保证搜索、曲线和核心指标可用。

## 10. 关键状态与文案

### 10.1 状态

- 首次启动且目录未同步。
- 开盘前等待。
- 实时采集中。
- 午间休市。
- 收盘补采和校准中。
- 历史已校准。
- 部分标的延迟。
- Collector 离线，但缓存可用。
- API 无法读取热库。
- 历史分区不存在或已超过保留期。
- 磁盘空间不足。
- 当前标的停牌、退市或本分钟无成交。

### 10.2 视觉语义

- 正常实时：绿色状态。
- 部分延迟或补采：黄色状态。
- 服务离线或严重覆盖不足：红色状态。
- 历史校准完成：中性“已校准”标识。
- 曲线缺口：保持断点并提供原因，不使用平滑线掩盖。

页面不只显示“加载失败”，而应说明失败对象、最后可用时间以及系统是否正在重试。

## 11. 容错与运行管理

- Collector、API 提供独立健康检查。
- 启动器逐个启动服务并显示 PID、端口和健康结果。
- 首期使用批处理/PowerShell 启动器；稳定后注册为 Windows 开机自启服务。
- 通达信连接池支持节点切换、指数退避和熔断。
- 单个标的失败不能终止本分钟其他标的采集。
- 每分钟提交失败时保留内存批次并有限重试；超过时间预算后写入缺口并进入补采队列。
- API 只读取已提交分钟，并在 Collector 离线时继续服务最后数据。
- 归档、清理和迁移都记录审计日志。
- 磁盘空间低于安全阈值时停止生成新归档并告警，不自动删除保留期内数据。
- 服务仅绑定本机地址；首期不提供局域网匿名访问。

## 12. 性能与质量验收

### 12.1 采集指标

- 全市场单分钟采集、计算和批量入库不超过 45 秒。
- 每只股票和每个板块都必须形成主力净额分钟序列；超大单、大单等分层序列必须按可用来源生成并标记质量。
- 每分钟覆盖率低于 99.5% 显示警告。
- 每分钟覆盖率低于 95% 显示故障。
- 收盘补采后仍未恢复的记录必须进入 `data_gap`。
- 任务重试不得生成重复唯一键记录。

### 12.2 查询指标

- 本地缓存命中时，切换板块或个股的主要内容在 500ms 内出现。
- 历史回放拖动分钟后，主要图表和排名在 300ms 内更新。
- 首屏避免加载全市场整日明细，只请求当前列表、当前标的和可视时间范围。
- API 查询不能持有阻塞 Collector 写入的长事务。

### 12.3 前端构建质量

当前基线主包约 1.7MB。实施时按板块工作台、个股工作台、K 线指标和回放模块进行动态加载，目标是降低初始包体并避免 ECharts 全量功能一次加载。

## 15. 实施阶段划分

该需求包含数据引擎、查询 API 和两个主要工作台，必须分阶段交付：

1. **基础设施与容量验证**：服务骨架、数据源适配器、市场目录、热库 schema、假数据压测。
2. **全市场分钟采集**：行情流水线、主力及分层资金混合采集、批次提交、覆盖率和缺口恢复。
3. **核心资金查询与工作台**：板块和个股主力净额分时 API、分层资金切换、板块排行、成分股排行和全局搜索。
4. **历史存储与资金回放**：收盘校准、Parquet、DuckDB、保留设置、回放快照和共享资金时间游标。
5. **个股完整行情能力**：行情头部、盘口、价格分时、K 线、指标和所属板块跳转。
6. **实时推送与完整回放交互**：播放控制、WebSocket、排名联动和断线退化。
7. **运行加固**：Windows 自启、健康检查、日志、磁盘保护、完整容量测试和迁移收尾。

每一阶段都必须有可运行验收结果，不能在全市场采集容量尚未达标前直接堆叠完整前端功能。

## 16. 最终成功标准

在单台目标 Windows 电脑上，从开盘前启动到收盘归档，系统可以持续生成沪深北全部 A 股和全部行业/概念板块的分钟记录。板块和个股都以主力资金净额分时曲线为核心，并支持主力、超大单、大单等可用分层口径。用户在实时或最近 30 个交易日回放中切换任意板块、成分股或自选股时，可以快速看到对应资金曲线、排名、行情和指标；采集延迟、估算、校准和数据缺口始终可见且可解释。采集、查询和维护彼此隔离，任一后台任务异常都不会无提示地阻断正常访问。
